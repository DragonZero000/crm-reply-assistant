# core-reply-service

Сервис готовит для менеджера черновик ответа клиенту и подсказку по допродаже. На вход он получает новое сообщение клиента и историю диалога из AmoCRM, на выход отдаёт черновик и подсказку. Отвечает строго по короткой базе знаний ([data/knowledge_base.json](data/knowledge_base.json)). Черновик никогда не отправляется клиенту автоматически.

Решения по архитектуре описаны в [openspec/changes/archive/2026-09-30-core-reply-service/design.md](openspec/changes/archive/2026-09-30-core-reply-service/design.md).

## Запуск

Нужен [uv](https://docs.astral.sh/uv/) и Python 3.12. Модель вызывается через OpenAI-совместимый Chat Completions API со структурированным ответом (`response_format: json_schema`). По умолчанию это локальный LM Studio на `http://127.0.0.1:1234`, в нём должна быть загружена модель из `LLM_MODEL`.

```bash
uv sync
cp .env.example .env        # при необходимости поменяйте адрес, модель, ключ
uv run uvicorn app.main:create_app --factory --port 8000
```

Если сервер модели недоступен, сервис всё равно запускается. На каждый запрос он возвращает шаблонный ответ и пометку для менеджера, что черновик не сформирован.

## Настройки (`.env`)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_BASE_URL` | `http://127.0.0.1:1234/v1` | адрес OpenAI-совместимого API |
| `LLM_API_KEY` | `lm-studio` | ключ API; LM Studio его не проверяет |
| `LLM_MODEL` | `ornith-1.0-35b-mtp-apex` | модель |
| `LLM_MAX_TOKENS` | `8000` | лимит токенов ответа |
| `LLM_TIMEOUT_SECONDS` | `300` | таймаут запроса к модели |
| `LLM_MAX_RETRIES` | `0` | повторы запроса к модели; для облачного провайдера разумно 1–2 |
| `LLM_PRICE_INPUT_PER_1M`, `LLM_PRICE_OUTPUT_PER_1M` | не заданы | цены за 1 млн токенов, только для оценки стоимости в логе |
| `HISTORY_LIMIT` | `10` | сколько последних сообщений клиента и менеджера передаётся модели |
| `KB_PATH`, `COMPLIANCE_RULES_PATH` | `data/…` | пути к базе знаний и стоп-листу |

## API

`POST /v1/reply`

```bash
curl -X POST http://localhost:8000/v1/reply \
  -H "Content-Type: application/json; charset=utf-8" \
  --data-binary @- <<'EOF'
{
  "message": "А за сколько дней привезут в Казань?",
  "history": [
    {"role": "client", "text": "Хочу заказать Омега-3 1000 мг"},
    {"role": "bot", "text": "Оператор скоро ответит"},
    {"role": "manager", "text": "Отлично, она в наличии"}
  ]
}
EOF
```

Роли в `history`: `client`, `manager`, `bot`, `system`. Модели передаются только сообщения `client` и `manager`, и только последние `HISTORY_LIMIT` из них.

Ответ:

```json
{
  "client_reply": "Доставка в Казань занимает от 2 до 7 рабочих дней…",
  "manager_hint": "Можно предложить:\n- Витамин D3 2000 МЕ, 90 таблеток — 690 ₽ — … — …",
  "used_kb_ids": ["faq_delivery", "omega3_1000"],
  "needs_human": false,
  "reason": null,
  "upsell": [
    {"product_id": "vit_d3_2000", "name": "…", "price": 690, "pitch": "…", "why_now": "…"}
  ],
  "compliance": {"triggered": false, "matches": [], "original_reply": null},
  "kb_version": "2026-09-30.2"
}
```

Что значат поля:
- `needs_human` и `reason`: нужен ли менеджер и почему. Возможные причины: `medical`, `no_kb_answer`, `complaint`, `other`. `reason` равен `null` тогда и только тогда, когда `needs_human=false`.
- `upsell`: товары для допродажи. Берутся только из `related_ids` тех карточек товаров, на которые опирается ответ. Название, цену и `pitch` сервис берёт из базы, модель пишет только `why_now`.
- `compliance`: результат проверки стоп-листом [data/compliance_rules.json](data/compliance_rules.json).
  - Сработал в ответе клиенту: черновик заменяется безопасным шаблоном, исходный текст кладётся в `original_reply`, выставляется `needs_human=true` и `reason=medical`.
  - Сработал в обосновании допродажи: эта позиция удаляется.
  - Сработал в заметке менеджеру: только отметка в `matches`.
  - Стоп-лист — страховка от явных формулировок («лечит», «снимет боль», «нормализует давление»), а не гарантия: перефразы и неявные намёки регулярками не ловятся. Основная защита — промпт и менеджер, который читает каждый черновик.
- При сбое модели сервис всё равно отвечает `200`: шаблонный ответ клиенту, `needs_human=true`, `reason=other` и пометка в `manager_hint` с видом сбоя (`timeout`, `api_error`, `refusal`, `max_tokens`, `invalid_output`, `client_error`). Пустой `client_reply` от модели тоже считается сбоем `invalid_output`.

`GET /health` возвращает `{"status": "ok", "kb_version": "…"}`.

## Диалог AmoCRM

Сервис принимает вебхук о новом сообщении в чате сделки, накапливает историю диалога и пишет черновик с подсказкой во **внутреннее примечание к сделке**. Клиенту ничего не отправляется. Решения и инструкция подключения реальной amoCRM описаны в [openspec/changes/archive/2026-09-30-amocrm-dialog-adapter/design.md](openspec/changes/archive/2026-09-30-amocrm-dialog-adapter/design.md) (раздел «Как подключить реальную amoCRM»).

- Входящее сообщение (`type=incoming`) считается сообщением клиента и запускает генерацию черновика в фоне. Вебхуку сервис отвечает сразу.
- Исходящее сообщение (`type=outgoing`) считается сообщением менеджера и только пополняет историю. Модель видит его и не повторяет то, что менеджер уже предложил.
- Товары из прошлых подсказок по этой сделке повторно не предлагаются.
- Повторная доставка того же сообщения (по `id`) игнорируется.

Режимы (`.env`):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `CRM_MODE` | `mock` | `mock`: примечания хранятся в памяти и видны на странице `/mock`. `amo`: примечания пишутся через REST API amoCRM |
| `WEBHOOK_SECRET` | пусто | токен в адресе вебхука `?token=…`; в режиме `amo` обязателен |
| `AMO_SUBDOMAIN` | пусто | поддомен аккаунта: `demo` → `demo.amocrm.ru` |
| `AMO_ACCESS_TOKEN` | пусто | долгосрочный токен приватной интеграции, не коммитить |

**Mock-чат.** Откройте `http://localhost:8000/mock`, введите номер сделки, выберите отправителя (клиент или менеджер) и отправьте сообщение. Страница шлёт его в `/webhooks/amo` в формате вебхука amoCRM, а примечание с черновиком появляется справа через 5–20 с. Диалог и примечания сделки в JSON: `GET /mock/leads/{lead_id}`. Эти эндпоинты есть только в режиме `mock`.

Вебхук вручную (Python, потому что `curl` в Windows портит кириллицу в аргументах):

```bash
uv run python -c "
import urllib.request, urllib.parse
body = urllib.parse.urlencode({
    'message[add][0][id]': 'msg-1', 'message[add][0][type]': 'incoming',
    'message[add][0][text]': 'Сколько идёт доставка в Казань?',
    'message[add][0][entity_type]': 'lead', 'message[add][0][entity_id]': '555',
}).encode()
print(urllib.request.urlopen('http://localhost:8000/webhooks/amo', body).read())
"
# → {"accepted":1,"queued":1}; через несколько секунд: curl http://localhost:8000/mock/leads/555
```

Ограничения:
- история, примечания mock-режима и выданные подсказки хранятся в памяти процесса. После перезапуска они теряются, поэтому запускайте сервис одним процессом, без нескольких воркеров;
- сообщения, пришедшие до запуска сервиса, неизвестны: REST API amoCRM не отдаёт тексты чатов;
- сообщения без сделки (неразобранные чаты) пропускаются с записью в лог;
- формат вебхука приближен к amoCRM, но с живым payload не сверялся. `AmoCrmClient` проверен только тестами с подменой HTTP, живого аккаунта не было.

## Логи и стоимость

На каждый вызов модели пишется одна строка `llm_call`, при успехе и при любом сбое:

```
llm_call lead_id=555 message_id=msg-1 model=omnicoder-9b outcome=ok latency_ms=8412 prompt_tokens=3104 completion_tokens=287 cost=n/a
llm_call lead_id=- message_id=- model=omnicoder-9b outcome=timeout latency_ms=300004 prompt_tokens=n/a completion_tokens=n/a cost=n/a
```

- `lead_id` и `message_id` заполнены, если вызов пришёл из вебхука; для `POST /v1/reply` стоит `-`.
- `outcome` — `ok` или вид сбоя. Передача менеджеру (`no_kb_answer`, `medical`) — это `ok`: модель ответила штатно.
- Текст сообщений, промпт и ключ API в лог не попадают.
- `n/a` — значение неизвестно (провайдер не вернул `usage` или вызов не дошёл до ответа).

**Стоимость** считается, только если заданы обе цены:

```
cost = prompt_tokens × LLM_PRICE_INPUT_PER_1M / 1 000 000 + completion_tokens × LLM_PRICE_OUTPUT_PER_1M / 1 000 000
```

Встроенных цен нет: модель может работать локально или на серверах компании, где цены за токен нет, а расход ресурсов виден по `latency_ms` и токенам. Для оценки на платном провайдере подставьте его тариф. Нагрузка прототипа — примерно 3,1 тыс. токенов промпта и 300 токенов ответа на одно сообщение. База знаний целиком идёт в системный промпт, поэтому почти вся стоимость — входные токены. Оценка верхняя: кэш префикса и скидки провайдера не учитываются. `prompt_tokens` в логе — готовый замер для условия перехода на RAG ([design.md](openspec/changes/archive/2026-09-30-quality-and-observability/design.md), решение 4).

**Таймаут и повторы.** По умолчанию `LLM_TIMEOUT_SECONDS=300` и `LLM_MAX_RETRIES=0`: запрос ждёт не дольше 300 с. SDK `openai` сам повторяет запрос дважды, в том числе после таймаута, поэтому без явного `0` один запрос мог бы ждать до 15 минут. У медленной локальной модели повтор после таймаута почти всегда снова заканчивается таймаутом, и шаблон с пометкой для менеджера полезнее ожидания. Для облачного провайдера разумно 1–2 повтора и меньший таймаут.

## Тесты

```bash
uv run pytest            # юнит-тесты, модель подменяется фейком, сеть не нужна
uv run pytest -m live    # живые проверки на реальной модели, нужен доступный LLM_BASE_URL
```

Юнит-тесты проверяют **гарантии кода** при заданном ответе модели: стоп-лист, очистку допродаж, валидацию входа, шаблон при сбое. Живые проверки смотрят на **поведение модели**. Ключевые сценарии собраны в [tests/test_scenarios.py](tests/test_scenarios.py): вопрос по базе, вопрос вне базы, модель поддалась медицинской провокации, медицинский вопрос и жалоба с попыткой допродажи, пустое сообщение, таймаут модели, битый ответ модели.

Результаты живых проверок (30.09.2026, LM Studio, `omnicoder-qwen3.5-9b-claude-4.6-opus-uncensored-v2`, промпт ≈3,1 тыс. токенов, 5–20 с на запрос):
- последние два прогона — 8 из 8; ранние прогоны на той же модели давали 6 из 8, результаты между запусками плавают;
- проверки смотрят на маршрутизацию (`needs_human`, `reason`, `used_kb_ids`, `upsell`), но не на точность фактов. 9B-модель иногда выдумывает детали (например, «2–3 дня» вместо «2–7 рабочих дней» из базы), поэтому черновик обязательно читает менеджер;
- на вопрос о беременности модель предлагала противопоказанный товар с медицинским обоснованием. Поэтому при `reason=medical` сервис очищает допродажи кодом, а в стоп-лист добавлено правило `health_support`.

## Что улучшили бы дальше

- **Наблюдаемость:** JSON-логи, метрики (Prometheus: длительность, токены, доля шаблонных ответов и передач менеджеру), алерты на рост доли сбоев, трейсинг (OpenTelemetry, Langfuse).
- **Надёжность вызова модели:** запасная модель или провайдер, circuit breaker, повторы с backoff под конкретного провайдера, асинхронный клиент вместо потоков.
- **Расходы:** суточный бюджет на токены, rate limiting, кэш префикса у провайдера; переход на RAG по условиям из [design.md](openspec/changes/archive/2026-09-30-core-reply-service/design.md) (база около 100+ записей или 30–50 тыс. токенов промпта).
- **Качество ответов:** eval-набор на 50+ реальных диалогов с проверкой точности фактов против базы (сейчас live-тесты проверяют маршрутизацию, но не факты), прогон нескольких запусков из-за нестабильности модели.
- **Данные:** постоянное хранилище истории и примечаний вместо памяти процесса.
- **Вход модели:** структурированная передача диалога (JSON-массив сообщений или отдельные chat-роли) вместо расшифровки с тегами. Сейчас текст клиента экранируется, но формат остаётся текстовым; смена формата требует повторных live-прогонов.
- **Медицинские формулировки:** семантическая проверка черновика (классификатор или LLM-судья) поверх стоп-листа, чтобы ловить перефразы и неявные обещания.
- **Стоп-лист:** тест на корпусе реальных корректных черновиков, чтобы ловить ложные срабатывания на пересказах базы, а не только на её текстах; общий словарь медицинских терминов с подстановкой в правила вместо повтора в каждом паттерне.
