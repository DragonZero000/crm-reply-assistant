## Context

Вызов модели идёт через `OpenAILLMClient.generate` ([app/llm.py](../../../../app/llm.py)). Все ошибки SDK превращаются в `LLMFailure(kind)`, а `ReplyService` отвечает на них шаблоном. После успешного вызова пишется строка с id, моделью, `finish_reason` и токенами. При сбое остаётся только `LLM failure: <kind>` из сервиса, без длительности и токенов.

Что мешает прототипу выглядеть надёжным:
- `openai.APITimeoutError` наследует `APIError` и попадает в `api_error`;
- `max_retries` не задан, SDK по умолчанию делает 2 повтора, и при `LLM_TIMEOUT_SECONDS=300` запрос может ждать до 15 минут;
- в логе вызова нет сделки: адаптер знает `lead_id` и `message_id`, но до клиента модели они не доходят;
- стоимость не считается. Модель может быть локальной, в облаке или на серверах компании, поэтому единой цены за токен нет.

## Goals / Non-Goals

**Goals:**
- по каждому вызову модели в логе видно исход, длительность, токены и оценку стоимости, если цены заданы;
- таймаут отличим от других сбоев, а время ожидания ограничено `LLM_TIMEOUT_SECONDS`;
- восемь ключевых сценариев собраны в одном читаемом файле тестов.

**Non-Goals:**
- JSON-логи, метрики, трейсинг, алерты;
- запасная модель или провайдер, circuit breaker;
- встроенные тарифы моделей;
- проверка точности фактов в ответах модели.

## Decisions

### 1. Лог пишет клиент модели, одна строка в `finally`
Строка `llm_call` пишется в `OpenAILLMClient.generate`: только там есть `usage`, исходная ошибка SDK и точное время вызова. Время меряется `time.perf_counter()`, исход записывается в `finally`, поэтому строка появляется при любом выходе, включая неожиданное исключение.

```
llm_call lead_id=555 message_id=msg-1 model=omnicoder-9b outcome=ok latency_ms=8412 prompt_tokens=3104 completion_tokens=287 cost=n/a
llm_call lead_id=- message_id=- model=omnicoder-9b outcome=timeout latency_ms=300004 prompt_tokens=n/a completion_tokens=n/a cost=n/a
```

- При `max_tokens` SDK кладёт `completion` в исключение, и токены берутся оттуда: это самый дорогой сбой, его стоит видеть.
- Строка `LLM failure: <kind>` в сервисе остаётся уровнем WARNING: она означает «клиенту ушёл шаблон», а `llm_call` описывает сам вызов.
- Текст сообщений и промпт в лог не пишутся: там персональные данные клиента.

*Альтернатива:* обёртка-декоратор над любым `LLMClient`. Отклонено: у обёртки нет доступа к `usage` и исходной ошибке, пришлось бы протаскивать их через `LLMFailure` и результат.

### 2. Формат `key=value`, а не JSON
Стандартный `logging.basicConfig` уже настроен. Строку `key=value` удобно читать в консоли на демо, и её разбирает большинство сборщиков логов (Loki, Datadog). JSON-логи попадают в «Что улучшили бы дальше».

### 3. Стоимость: формула плюс необязательные цены
`LLM_PRICE_INPUT_PER_1M` и `LLM_PRICE_OUTPUT_PER_1M` имеют тип `float | None`, `ge=0`, по умолчанию `None`. Стоимость считается функцией `estimate_cost(prompt_tokens, completion_tokens, settings) -> float | None` и равна `None`, если не задана хотя бы одна цена или нет токенов. В лог пишется с 6 знаками после точки, в единицах, в которых заданы цены (валюта в коде не фиксируется).

*Почему не встроенные цены:* цена зависит от модели и тарифа и быстро устаревает. Для модели на своих серверах цены за токен нет вовсе, там расход ресурсов — это `latency_ms` и число токенов. Ноль по умолчанию выглядел бы как «бесплатно», поэтому пишется `n/a`.

В README — формула и реальная нагрузка прототипа: ≈3,1 тыс. токенов промпта и ≈300 ответа на сообщение. Этого хватает, чтобы подставить тариф своей модели.

### 4. Вся база в контексте остаётся, лог даёт замер для перехода на RAG
Решение из [core-reply-service/design.md](../2026-09-30-core-reply-service/design.md#1-вся-база-в-контексте-без-rag) не меняется: база целиком идёт в system prompt. Поэтому почти вся стоимость приходится на входные токены, и `prompt_tokens` в `llm_call` — готовый замер для условия перехода. Переходим на RAG (сначала оглавление базы и инструмент `get_entry(id)`), если выполнено любое из условий:
- `prompt_tokens` стабильно 30–50 тыс. или база выросла примерно до 100+ записей;
- модель путает похожие записи (неверные `used_kb_ids`), и переписывание записей не помогает;
- в базу добавляются длинные документы, а не короткие ответы.

До этого дешевле включить кэш префикса у провайдера: system prompt стабилен и собирается детерминированно.

### 5. Таймаут — отдельный `kind`, повторов по умолчанию нет
- `except openai.APITimeoutError` ставится раньше `except openai.APIError` и выдаёт `LLMFailure("timeout")`.
- `openai.OpenAI(..., max_retries=settings.llm_max_retries)`, `LLM_MAX_RETRIES=0` по умолчанию, `ge=0`.
- `LLM_TIMEOUT_SECONDS` остаётся 300: неизвестно, какая модель будет у проверяющего, а крупной локальной модели может понадобиться много времени.

Почему 0: SDK повторяет и таймауты, а у медленной локальной модели повтор после таймаута почти всегда снова заканчивается таймаутом. Черновик читает менеджер, поэтому шаблон с пометкой лучше пятнадцати минут ожидания. Для облачного провайдера в README рекомендуется 1–2 повтора с меньшим таймаутом.

`manager_hint` при таймауте: «Черновик не сформирован: модель не ответила за отведённое время (timeout). Ответ клиенту — шаблон, ответьте вручную.» Для остальных видов сбоя текст прежний.

*Альтернатива:* запасная модель. Отклонено для прототипа: вторая модель — это второй набор промпт-проверок и live-тестов, а шаблон и передача менеджеру уже закрывают риск.

### 6. Контекст сделки — явный параметр
`@dataclass(frozen=True) class CallContext: lead_id: int | None = None; message_id: str | None = None` в `app/llm.py`. Параметр `context: CallContext | None = None` добавляется в `LLMClient.generate` и `ReplyService.reply`. `DialogAdapter.generate` передаёт `CallContext(event.lead_id, event.message_id)`, эндпоинт `/v1/reply` не передаёт ничего.

*Альтернатива:* `contextvars`. Отклонено: неявная передача сложнее для чтения. Фоновые задачи FastAPI выполняются в потоках, и контекст нужно было бы копировать вручную.

### 7. `tests/test_scenarios.py` — витрина, а не замена
Восемь тестов через `POST /v1/reply` с `FakeLLMClient`. Докстринг файла: «гарантии кода при заданном ответе модели; поведение самой модели — в test_live.py».

| # | Сценарий | Фейк модели | Проверка |
|---|---|---|---|
| 1 | Вопрос по базе | ответ, `faq_delivery`, `omega3_1000` + upsell | `needs_human=false`, upsell обогащён из базы |
| 2 | Вопрос вне базы | `no_kb_answer` | `needs_human=true`, `reason=no_kb_answer` |
| 3 | Медицинская провокация, модель поддалась | «Омега-3 вылечит суставы» | ответ заменён шаблоном, `original_reply` сохранён, `reason=medical`, upsell пуст |
| 4 | Медицинский вопрос с попыткой допродажи | `medical` + upsell | upsell очищен кодом |
| 5 | Жалоба с попыткой допродажи | `complaint` + upsell | upsell пуст |

## Risks / Trade-offs

- [Синхронный `/v1/reply` может ждать до 300 с и занимать поток] → в прототипе приемлемо; основной путь — вебхук с фоновой генерацией. Лимит конфигурируется.
- [Без повторов кратковременный разрыв соединения даёт шаблон] → менеджер видит пометку и отвечает сам; `LLM_MAX_RETRIES` можно поднять.
- [Локальные серверы иногда не возвращают `usage`] → поля `n/a`, ответ не ломается; в логе видно, что токены неизвестны.
- [Оценка стоимости не учитывает кэш префикса и скидки провайдера] → в README указано, что это верхняя оценка по базовому тарифу.
- [Изменение сигнатуры `LLMClient.generate`] → параметр необязательный; `FakeLLMClient` обновляется в том же изменении.
- [Сценарии частично дублируют существующие тесты] → осознанно: файл служит обзором, а подробные проверки остаются в модульных тестах.

## Migration Plan

Контракт API и формат примечания не меняются. Новые настройки необязательны. Единственное заметное изменение поведения: SDK больше не повторяет запросы. Чтобы вернуть прежнее поведение, задать `LLM_MAX_RETRIES=2`.
