## Context

Проект пустой, это первое изменение. Сервис вызывается на стороне интеграции с AmoCRM: ей передаётся новое сообщение клиента и история диалога, а она получает черновик ответа и подсказку для менеджера. Ответ клиенту никогда не отправляется автоматически — его видит и правит менеджер.

Ограничения:
- база знаний маленькая: 5 FAQ и 8–10 карточек товаров (вымышленные данные);
- товары про здоровье: медицинские обещания недопустимы ни в ответе клиенту, ни в подсказке по допродаже (менеджер может повторить её клиенту);
- стек: Python 3.12, FastAPI, Pydantic v2, pytest; секреты только из `.env`.

## Goals / Non-Goals

**Goals:**
- черновик ответа строго по базе знаний, с честной передачей менеджеру, когда ответа нет;
- допродажи, которые невозможно выдумать: только товары из базы, формулировки из базы;
- медицинские обещания ловятся кодом, а не только инструкцией модели;
- поведение проверяемо юнит-тестами без обращения к модели.

**Non-Goals:**
- автоотправка ответа клиенту и интеграция с API AmoCRM;
- RAG и векторный поиск;
- хранение диалогов, аутентификация, rate limiting;
- повторная генерация после срабатывания стоп-листа.

## Decisions

### 1. Вся база в контексте, без RAG
База целиком (≈5–10 тыс. токенов вместе с правилами) передаётся в системном промпте при каждом запросе.

Почему не RAG:
- модель видит всю базу, поэтому «ответа в базе нет» — достоверный вывод; при top-k поиске промах поиска неотличим от отсутствия ответа;
- для допродаж нужны связи между товарами, а поиск находит то, о чём спросили, а не то, что к этому подходит;
- нет инфраструктуры эмбеддингов и индекса, а экономии токенов при таком размере нет.

Системный промпт (правила + база) стабилен, история и новое сообщение идут после него. Текст базы собирается детерминированно, без дат и id запроса: так работает кэш префикса у провайдеров, которые его поддерживают (LM Studio переиспользует префикс автоматически, OpenAI кэширует его сам при длине от ~1 тыс. токенов).

**Условия перехода на RAG** (любое из):
- база выросла примерно до 100+ записей или 30–50 тыс. токенов (замер через подсчёт токенов API, а не на глаз);
- на тестовом наборе модель путает похожие записи (неверные `used_kb_ids`), и переписывание записей не помогает;
- в базу добавляются длинные документы (инструкции, сертификаты), а не короткие ответы.

Первый шаг перехода — оглавление базы в контексте и инструмент `get_entry(id)`, векторный поиск — только если этого окажется мало.

### 2. Модель и вызов
OpenAI-совместимый Chat Completions API через SDK `openai`: `chat.completions.parse()` с Pydantic-моделью в `response_format` (JSON Schema). Для разработки и тестов — локальный LM Studio (`http://127.0.0.1:1234/v1`), для продакшена достаточно сменить `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL`. Адрес без пути дополняется до `/v1`: иначе LM Studio отвечает 200 с ошибкой в теле, и это выглядит как пустой ответ модели.

Изначально планировался Anthropic API; перешли на OpenAI-совместимый, чтобы тестировать на локальной модели без ключа и оплаты.

Вызов модели скрыт за небольшим интерфейсом (`LLMClient` с одним методом), чтобы юнит-тесты подставляли фейковую реализацию, а провайдера можно было заменить. Альтернатива — вызывать SDK напрямую в обработчике — отвергнута: тесты стали бы зависеть от сети и ключа.

### 3. Схема ответа модели уже схемы ответа сервиса
Модель заполняет только то, что может знать:

```
client_reply  string
used_kb_ids   [KbId]                       ← enum из id базы
needs_human   bool
reason        medical | no_kb_answer | complaint | other | null
upsell        [{product_id: ProductId, why_now: string}]   ← enum из id товаров
manager_note  string | null
```

Сервис проверяет результат и дополняет его: `name`/`price`/`pitch` из базы, `compliance`, `manager_hint`, `kb_version`.

- `KbId` и `ProductId` — enum, собранные из базы при старте. Схема с enum не даёт модели сослаться на несуществующую запись. Отдельного механизма цитат в структурированном ответе нет, поэтому `used_kb_ids` и есть механизм ссылок.
- `confidence` (число) отвергнуто: самооценка модели плохо откалибрована, на неё нельзя опереться ни в маршрутизации, ни в тестах. `needs_human` + `reason` проверяемы: `assert reason == "no_kb_answer"`.
- Инвариант «`reason=null` ⇔ `needs_human=false`» проверяет Pydantic-валидатор после ответа модели, а не схема (через `anyOf` это громоздко).

### 4. История как расшифровка, а не чат
Сообщения `client`/`manager` после фильтрации ролей и обрезки до `HISTORY_LIMIT` передаются одним пользовательским сообщением в виде размеченной расшифровки (`<history>…</history><new_message>…</new_message>`). Альтернатива — отдавать реплики менеджера как роль `assistant` — отвергнута: модель считала бы их своими, а задача — не продолжить чат, а подготовить черновик. Фильтрация ролей выполняется до обрезки, иначе сообщения бота занимали бы окно.

### 5. Допродажи: модель выбирает, база формулирует
Кандидаты — `related_ids` карточек товаров из `used_kb_ids`. Модели разрешено включать в `used_kb_ids` карточку товара, который обсуждается в истории, даже если ответ дан по FAQ. Модель выбирает 0–2 кандидата и пишет `why_now` (почему уместно в этом диалоге). Текст о самом товаре — `pitch` из карточки, согласованный заранее. Код отбрасывает позиции вне кандидатов, дубли, лишние сверх двух и все позиции при `reason=complaint` или `reason=medical` (живые проверки показали, что локальная модель предлагает товар даже на вопрос о беременности, причём противопоказанный).

Отвергнутые варианты: свободный текст допродажи от модели (выдумывает товары и свойства); `product_id` без `pitch` из базы (модель сочиняет обоснование, в котором появляются медицинские обещания).

### 6. Стоп-лист: код, а не только промпт
Правила в `compliance_rules.json` (`rule_id`, regex по фразе, описание). Нормализация: нижний регистр, `ё` → `е`. Правила — фразы, а не голые основы слова: основа «лекарств» поймала бы обязательную оговорку «не является лекарственным средством».

Что проверяется и что происходит при срабатывании:

```
client_reply    → шаблон, original_reply сохраняется, needs_human=true, reason=medical
upsell.why_now  → позиция удаляется, ответ клиенту не трогается
manager_note    → только отметка в compliance.matches
```

Если модель указала другую причину (например, `complaint`), срабатывание фильтра её перезаписывает на `medical`: подмена черновика — более важный сигнал, а жалоба остаётся видна в `manager_note`. Тестами проверяется, что база и оба шаблона проходят фильтр без срабатываний.

### 7. Сбой модели — это ответ 200, а не ошибка
Отказ модели (`message.refusal`, `finish_reason=content_filter`), обрыв (`finish_reason=length`), невалидный JSON, ошибка API после встроенных повторов SDK и любая другая ошибка вызова превращаются в ответ с шаблоном, `needs_human=true`, `reason=other` и пометкой в `manager_hint`. Интеграция с CRM получает предсказуемый ответ одного формата, а менеджер видит, что черновика нет. Ошибка пишется в лог.

### 8. Данные и настройки
- `knowledge_base.json`, `compliance_rules.json` — в репозитории, читаются и проверяются при старте; ошибка в данных останавливает запуск.
- Настройки через pydantic-settings из `.env`: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `LLM_MAX_TOKENS`, `LLM_TIMEOUT_SECONDS`, `HISTORY_LIMIT=10`, пути к файлам данных.

## Risks / Trade-offs

- [Стоп-лист не ловит перефразированные обещания («уйдут боли», «забудете о проблемах»)] → правила пополняются по мере находок; промпт с примерами «можно/нельзя»; финальный контроль — менеджер, ответ всегда черновик.
- [Ложные срабатывания стоп-листа на безобидный текст] → правила по фразам, тест на всех текстах базы и шаблонах; менеджер видит исходный черновик в `compliance.original_reply` и может его использовать.
- [Модель отвечает из общих знаний, когда база молчит] → явное правило в промпте, сценарии «вне базы» в живых проверках; `used_kb_ids` показывает, на чём основан ответ.
- [Модель завышает `needs_human` и отправляет менеджеру простые вопросы] → приемлемо для прототипа (ошибка в безопасную сторону); измеряется на живых проверках.
- [Локальная модель слабее и медленнее облачной: пропускает правила, долго отвечает] → живые проверки показывают, какие сценарии проходят; таймаут вынесен в настройки; стоп-лист и проверки кодом не зависят от качества модели.
- [Сервер без поддержки JSON Schema в `response_format` вернёт свободный текст] → такой ответ не проходит валидацию и превращается в шаблон; сервер модели нужно выбирать с поддержкой структурированного вывода.

## Migration Plan

Не применимо: новый сервис без предыдущей версии. Откат — остановка сервиса; интеграция продолжает работать вручную.

## Open Questions

- Какая модель и провайдер будут в продакшене — решение отложено; код от этого не зависит, меняются только настройки.
- Тексты безопасного шаблона и шаблона сбоя — согласовать с тем, кто отвечает за коммуникацию с клиентами (в прототипе — нейтральные формулировки).
