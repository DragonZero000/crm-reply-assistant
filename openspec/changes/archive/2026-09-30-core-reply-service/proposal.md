## Why

Менеджеры вручную отвечают клиентам в AmoCRM на однотипные вопросы (доставка, оплата, возврат, состав товара) и не всегда вспоминают, что уместно предложить к покупке. Нужен сервис, который по сообщению клиента и истории диалога готовит черновик вежливого ответа строго по базе знаний и подсказку по допродаже. Товары про здоровье, поэтому медицинские обещания в тексте недопустимы, и это должен проверять код, а не только модель.

## What Changes

- Новый HTTP-сервис на FastAPI с эндпоинтом `POST /v1/reply`: принимает новое сообщение клиента и историю диалога, возвращает черновик ответа клиенту и подсказку менеджеру.
- База знаний `knowledge_base.json` (вымышленные данные): 5 FAQ (доставка, оплата, возврат, сроки, гарантия) и 8–10 карточек товаров с полями `price`, `pitch`, `related_ids`, у части — противопоказания.
- Вся база целиком передаётся модели в системном промпте (без RAG), ответ модели — структурированный JSON по схеме, где id записей и товаров ограничены enum из базы.
- Обработка истории: в модель уходят только роли `client` и `manager`, последние `HISTORY_LIMIT` сообщений (по умолчанию 10).
- Когда ответа в базе нет, по медицинским вопросам и жалобам — `needs_human=true` с причиной `reason` (`medical`, `no_kb_answer`, `complaint`, `other`).
- Допродажи только из `related_ids` карточек, на которые ссылается ответ; название, цена и формулировка (`pitch`) подставляются из базы.
- Пост-фильтр по стоп-листу медицинских обещаний: при срабатывании в `client_reply` подставляется безопасный шаблон, ставится `needs_human=true`, менеджер видит, что именно сработало, и исходный черновик.
- Безопасный ответ-заглушка при ошибке модели (отказ, обрыв, невалидный JSON, сетевая ошибка).

**Входит в прототип:**
- один эндпоинт генерации черновика и `GET /health`;
- база знаний и стоп-лист в JSON-файлах, читаются при старте;
- юнит-тесты с подменой модели и небольшой набор живых проверок на реальной модели.

**Сознательно не делается:**
- автоотправка ответа клиенту — ответ всегда черновик для менеджера;
- интеграция с AmoCRM (вебхуки, авторизация, запись в сделку) — сервис принимает уже подготовленный JSON;
- RAG, векторная БД, админка для редактирования базы;
- хранение диалогов, аутентификация вызывающей стороны, rate limiting;
- повторная генерация ответа после срабатывания стоп-листа.

## Capabilities

### New Capabilities
- `knowledge-base`: формат и загрузка базы знаний (FAQ и карточки товаров), проверка целостности, версия базы.
- `reply-generation`: эндпоинт `/v1/reply`, подготовка истории, вызов модели, формат ответа, поведение при отсутствии ответа в базе и при ошибках модели.
- `upsell-hints`: выбор допродаж из `related_ids`, проверка кандидатов, обогащение данными из базы, сборка `manager_hint`.
- `compliance-filter`: стоп-лист медицинских обещаний, проверка полей ответа, замена шаблоном и отчёт для менеджера.

## Impact

- Новый код: пакет приложения (FastAPI, Pydantic-модели, клиент LLM, фильтр), файлы данных `knowledge_base.json` и `compliance_rules.json`.
- Зависимости: `fastapi`, `uvicorn`, `pydantic`, `pydantic-settings`, `openai`, `pytest`, `httpx`.
- Секреты: ключ API модели (если провайдер его требует) в `.env`, в репозиторий не попадает; `.env.example` без значений.
- Внешняя система: OpenAI-совместимый API модели (для тестов — локальный LM Studio); при его недоступности сервис отвечает заглушкой, а не ошибкой.
