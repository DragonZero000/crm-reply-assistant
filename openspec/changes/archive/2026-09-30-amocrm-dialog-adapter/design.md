## Context

Ядро сервиса (`ReplyService`, `POST /v1/reply`) готово. Оно синхронно принимает `message` + `history` и возвращает черновик и подсказку. На тестовой модели ответ занимает 5–20 с, таймаут — до 300 с. Целевая модель в продакшене сильнее тестовой 9B, но это тоже секунды.

Нужно встроить сервис в диалог сделки AmoCRM. Ограничения:
- аккаунта amoCRM нет, поэтому основной режим — mock, а интеграция с amoCRM — заготовка, проверенная тестами с подменой HTTP;
- черновик никогда не уходит клиенту автоматически (главное правило сервиса);
- времени — пара часов, поэтому только то, что можно показать и проверить локально.

## Goals / Non-Goals

**Goals:**
- один входной путь для mock и amoCRM: вебхук в amo-формате;
- генерация на сообщение клиента, учёт реплик менеджера в истории;
- результат — внутреннее примечание к сделке;
- подключение реальной amoCRM без изменения кода, только через `.env` и настройки аккаунта.

**Non-Goals:**
- отправка сообщений клиенту (Chats API, Salesbot);
- OAuth с обновлением токенов, постоянное хранилище, работа в нескольких процессах;
- изменение контракта `POST /v1/reply`.

## Decisions

### 1. Схема адаптера

```
  /mock (HTML) ──┐  form-urlencoded, как у amoCRM
  amoCRM ────────┴─▶ POST /webhooks/amo?token=…      → 200 сразу
                        │
                        ▼
                  parse_amo_webhook(body) → [ChatEvent(lead_id, role, text, message_id)]
                        │
                        ▼
                  DialogStore (память, ключ lead_id)
                    • seen message_id  → дубликат? пропустить
                    • history          → добавить сообщение
                    • offered_products → выданные допродажи
                        │
            role=manager┴role=client
               (стоп)       ▼  BackgroundTasks
                  ReplyService.reply(request, exclude=offered_products)
                        ▼
                  format_note(response) → CrmClient.add_note(lead_id, text)
                        ├─ MockCrmClient  — список в памяти → GET /mock/leads/{id}
                        └─ AmoCrmClient   — POST /api/v4/leads/{id}/notes
```

`ReplyService` не знает о CRM; адаптер собирает `ReplyRequest` из хранилища и вызывает сервис так же, как это делает `/v1/reply`.

### 2. Вебхук + примечание, а не Chats API или Salesbot
- **Вебхук + REST-примечание** (выбрано): вебхук на событие сообщения в чате настраивается в интерфейсе аккаунта, примечание пишется одним REST-запросом с долгосрочным токеном приватной интеграции. Примечание видит только менеджер — это совпадает с правилом «черновик не уходит клиенту».
- **Chats API (amojo)**: чтобы зарегистрировать свой канал, нужно писать в техподдержку amoCRM за `channel_id` и секретом (дни), плюс подпись запросов HMAC. Главное — это API для отправки сообщений *в чат клиенту*, а нам это не нужно.
- **Salesbot**: чтобы получить ответ внешнего сервиса, нужен шаг `widget_request`, который требует установленного виджета и обратного вызова `salesbot/{id}/continue`. Бот пишет клиенту, то есть это та же автоотправка. Возможное развитие — кнопка «отправить черновик» по решению менеджера, но это другая задача.

### 3. Один входной формат для mock и amoCRM
Mock-страница шлёт тот же form-urlencoded, что и amoCRM, в тот же эндпоинт. Альтернатива — отдельный JSON-эндпоинт для mock — проще в UI, но тогда mock не проверяет разбор amo-формата, а именно он главный риск при подключении. `CrmClient` абстрагирует только исходящую сторону.

Приблизительный формат (поля сверяются с реальным payload при подключении, см. раздел 9):

```
account[id]=31000000&account[subdomain]=demo
message[add][0][id]=5f1c…            ← id сообщения, ключ дедупа
message[add][0][chat_id]=…&message[add][0][talk_id]=42&message[add][0][contact_id]=777
message[add][0][text]=А доставка в Казань?
message[add][0][created_at]=1727700000
message[add][0][type]=incoming        ← incoming → client, outgoing → manager
message[add][0][entity_type]=lead&message[add][0][entity_id]=555   ← сделка
message[add][0][author][id]=…&message[add][0][author][type]=external&message[add][0][author][name]=Иван
message[add][0][origin]=telegram
```

Тело разбирается `urllib.parse.parse_qsl` из `await request.body()`, а не через `Form(...)` FastAPI: нужен произвольный набор ключей со скобками, и не нужна зависимость `python-multipart`. Парсер — чистая функция `body → list[ChatEvent]` с отдельными юнит-тестами.

### 4. Ответ сразу, генерация в фоне
amoCRM ждёт быстрый ответ на вебхук и повторяет доставку при таймауте или ошибке; вебхук, который постоянно сбоит, аккаунт может отключить. Модель отвечает секунды, поэтому эндпоинт только разбирает тело, обновляет историю и ставит генерацию в `BackgroundTasks`. Альтернатива — очередь (Celery/RQ) — избыточна для прототипа. `BackgroundTasks` для sync-функций выполняется в пуле потоков, поэтому `DialogStore` и `MockCrmClient` защищены `threading.Lock`.

Ошибки в фоне (сбой записи примечания) только логируются: вебхуку уже ответили `200`. Сбой модели обрабатывает сам `ReplyService` — примечание всё равно создаётся с шаблоном.

### 5. Дедупликация и история в памяти
`DialogStore` хранит по `lead_id`: список сообщений (`client`/`manager`), множество уже выданных `product_id`; глобально — множество обработанных id сообщений. Сообщение добавляется в историю и помечается обработанным синхронно в эндпоинте, до фоновой задачи, чтобы повторная доставка вебхука сразу отсекалась.

Черновик на сообщение клиента строится из истории *до* этого сообщения (`history`) и самого сообщения (`message`). Обрезку до `HISTORY_LIMIT` и фильтр ролей делает существующий `prepare_history`.

Почему в памяти: публичный REST API v4 не отдаёт тексты сообщений чатов (они доступны только владельцу канала через amojo), поэтому историю всё равно приходится копить самим из вебхуков. Постоянное хранилище (SQLite) — первое, что стоит добавить после прототипа; интерфейс `DialogStore` позволяет заменить реализацию.

### 6. Не повторять допродажу: промпт + фильтр кодом
- **A. Промпт (основной механизм).** Реплики менеджера уже попадают в `<history>`. В правила допродаж добавляется «не предлагай товар, который менеджер уже предлагал клиенту в истории». Модель 9B используется только для тестов; целевая модель надёжнее следует таким правилам, и только модель может понять, что «добавлю витамин Д» — это `vit_d3_2000`.
- **B. Фильтр кодом (страховка).** `DialogStore` запоминает `product_id` из каждой записанной подсказки; `ReplyService.reply(request, exclude=…)` передаёт их в `filter_upsell`, который отбрасывает исключённые. Не зависит от модели и от окна `HISTORY_LIMIT` (ранний обмен мог выпасть из истории). Ограничение: «сервис подсказал» ≠ «менеджер предложил», поэтому товар, который менеджер проигнорировал, повторно не всплывёт — для черновика это приемлемо.
- **C. Сопоставление текста менеджера с товарами** (не делаем): в базе нет синонимов, а названия («Витамин D3 2000 МЕ, 90 таблеток») и живая речь («витамин Д3») расходятся. Потребует поля `aliases` в базе и правки валидации `kb.py`.

Параметр `exclude` необязательный и не входит в `ReplyRequest`, поэтому контракт `POST /v1/reply` не меняется.

### 7. Формат примечания
Примечание — обычный текст (`note_type=common`):

```
Черновик ответа (не отправлен клиенту)
<client_reply>

Подсказка менеджеру
<manager_hint>

[если compliance.original_reply]
Исходный черновик заблокирован фильтром медицинских формулировок:
<original_reply>

База знаний: <kb_version>
```

`manager_hint` уже содержит причину передачи менеджеру, сработавшие правила стоп-листа и допродажи, поэтому отдельно они не дублируются. Исходный заблокированный текст выводится явно: в JSON-ответе он лежит в `compliance.original_reply`, а в примечании менеджер JSON не видит.

### 8. Настройки и режимы
| Переменная | По умолчанию | Назначение |
|---|---|---|
| `CRM_MODE` | `mock` | `mock` или `amo` |
| `WEBHOOK_SECRET` | пусто | токен в `?token=`; в режиме `amo` обязателен |
| `AMO_SUBDOMAIN` | пусто | `demo` → `https://demo.amocrm.ru` |
| `AMO_ACCESS_TOKEN` | пусто | долгосрочный токен приватной интеграции, `SecretStr` |

В режиме `amo` недостающие настройки останавливают запуск (валидатор `Settings`). Токен в URL, а не подпись, потому что вебхуки аккаунта amoCRM не подписываются; сравнение через `secrets.compare_digest`. В mock-режиме страница `/mock` подставляет токен сама, если он задан.

`AmoCrmClient` использует `httpx.Client` с таймаутом и принимает транспорт в конструкторе — тесты подменяют его `httpx.MockTransport` и проверяют URL, заголовок и тело. Против живой amoCRM клиент не проверялся, это указано в README.

### 9. Как подключить реальную amoCRM
1. **Аккаунт и канал.** В аккаунте amoCRM (подойдёт пробный) подключить канал чата: Telegram-бот или «Чат на сайте». Без подключённого канала событий о сообщениях не будет. Проверить, что входящее сообщение создаёт сделку (или привязать чат к сделке вручную): сообщения без сделки сервис пропускает.
2. **Приватная интеграция.** «amoМаркет» → «Создать интеграцию» → «Внешняя интеграция», доступ к данным аккаунта. На вкладке «Ключи и доступы» сгенерировать **долгосрочный токен** — он заменяет OAuth-обмен кодов и обновление токенов.
3. **`.env`**:
   ```
   CRM_MODE=amo
   AMO_SUBDOMAIN=<поддомен без .amocrm.ru>
   AMO_ACCESS_TOKEN=<долгосрочный токен>
   WEBHOOK_SECRET=<случайная строка, например из secrets.token_urlsafe(32)>
   ```
4. **Публичный адрес.** Запустить сервис и туннель: `cloudflared tunnel --url http://localhost:8000` или `ngrok http 8000`. На продакшене — обычный HTTPS-адрес.
5. **Сверить формат payload.** Сначала указать в вебхуке адрес `https://webhook.site/…`, отправить в канал сообщение от клиента и ответ менеджера, сохранить оба сырых тела как фикстуры `tests/fixtures/amo_*.txt` и прогнать тесты парсера. Если ключи отличаются от раздела 3 — поправить только `parse_amo_webhook`.
6. **Вебхук.** «Настройки» → «Интеграции» → «Web hooks» (или `POST /api/v4/webhooks`): адрес `https://<туннель>/webhooks/amo?token=<WEBHOOK_SECRET>`, событие — только сообщения в чате. **Не подписываться** на события примечаний сделок: наше примечание вызовет вебхук снова.
7. **Проверка.** Написать в канал от клиента → через несколько секунд в сделке появляется примечание «Черновик ответа (не отправлен клиенту)». Ответить от менеджера → примечания нет, но следующий черновик учитывает реплику.

### 10. База знаний в контексте, без RAG
Решение из предыдущего изменения не меняется: вся база (≈15 записей) передаётся в системном промпте, адаптер на это не влияет — он только собирает `history`. Переход на RAG нужен, если база вырастет примерно до 100+ записей или 30–50 тыс. токенов, если модель начнёт путать похожие записи на тестовом наборе или если в базу добавят длинные документы. Правило о предложениях менеджера добавляется в статичную часть промпта, поэтому кэш префикса не ломается.

## Risks / Trade-offs

- [Формат вебхука amoCRM воспроизведён по памяти и документации, а не по живому payload] → парсер — изолированная функция, шаг 5 раздела 9 сверяет формат до включения; отличия правятся в одном месте.
- [История и примечания теряются при перезапуске; сообщения до запуска сервиса неизвестны] → явно указано в README; `DialogStore` заменяем на SQLite без изменения эндпоинтов.
- [Несколько воркеров uvicorn не делят память] → запуск в одном процессе; для масштабирования нужно внешнее хранилище.
- [Клиент пишет два сообщения подряд → две генерации, второй черновик учитывает первое сообщение, первый — нет] → для прототипа приемлемо; позже — debounce по сделке.
- [Фильтр B не даёт повторить товар, который менеджер проигнорировал] → осознанный выбор в пользу «не надоедать»; подсказки легко сбросить перезапуском, в продакшене — TTL.
- [Исходящие сообщения Salesbot или автоответов тоже приходят как `outgoing` и считаются репликами менеджера] → для прототипа приемлемо; при подключении можно фильтровать по `author[type]`.
- [Сбой записи примечания в фоне не виден вызывающей стороне] → логирование с `lead_id`; повторов нет, чтобы не плодить дубли.
- [`AmoCrmClient` не проверен на живом API] → тесты с `MockTransport` фиксируют запрос по документации; первая живая проверка — шаг 7 раздела 9.

## Open Questions
