# crm-dialog-adapter Specification

## Purpose
Адаптер диалога сделки AmoCRM: приём вебхука о сообщениях чата, роли и дедупликация, история по сделке, генерация черновика только на сообщение клиента и запись результата во внутреннее примечание через CrmClient (режимы mock и amo).

## Requirements
### Requirement: Приём вебхука о сообщении в чате
Система SHALL принимать `POST /webhooks/amo` с телом `application/x-www-form-urlencoded` в формате, приближенном к событию amoCRM «новое сообщение» (`message[add][N][…]`), и отвечать `200` до начала генерации черновика. Запрос с отсутствующим или неверным параметром `token` (сравнение с `WEBHOOK_SECRET`) MUST отклоняться с кодом `401` без обработки сообщений. Если `WEBHOOK_SECRET` не задан (допустимо только в mock-режиме), токен не проверяется.

#### Scenario: Корректный вебхук
- **GIVEN** `WEBHOOK_SECRET=s3cret`
- **WHEN** приходит `POST /webhooks/amo?token=s3cret` с одним входящим сообщением по сделке `555`
- **THEN** сервис отвечает `200`, не дожидаясь ответа модели, а генерация запускается в фоне

#### Scenario: Неверный токен
- **GIVEN** `WEBHOOK_SECRET=s3cret`
- **WHEN** приходит `POST /webhooks/amo?token=wrong`
- **THEN** сервис отвечает `401`, сообщение не попадает в историю, генерация не запускается

#### Scenario: Несколько сообщений в одном вебхуке
- **WHEN** вебхук содержит `message[add][0]` и `message[add][1]`
- **THEN** оба сообщения обрабатываются в порядке индексов

### Requirement: Разбор сообщения и роли
Для каждого сообщения система SHALL извлекать id сообщения, текст, тип и id сделки (`entity_id` при `entity_type=lead`). Тип `incoming` MUST соответствовать роли `client`, тип `outgoing` — роли `manager`. Сообщение без сделки, с пустым текстом или неизвестным типом SHALL пропускаться с записью в лог, не вызывая ошибку всего вебхука.

#### Scenario: Входящее сообщение клиента
- **GIVEN** `message[add][0][type]=incoming`, `entity_type=lead`, `entity_id=555`
- **WHEN** вебхук разобран
- **THEN** получено событие с ролью `client` по сделке `555`

#### Scenario: Сообщение без сделки
- **GIVEN** сообщение из неразобранного чата без `entity_id` сделки
- **WHEN** вебхук обработан
- **THEN** сообщение пропущено, в лог записана причина, сервис ответил `200`

#### Scenario: Сообщение без текста
- **GIVEN** сообщение только с вложением и пустым `text`
- **WHEN** вебхук обработан
- **THEN** сообщение пропущено без генерации

### Requirement: Дедупликация сообщений
Система SHALL обрабатывать каждое сообщение (по id сообщения) не более одного раза в рамках процесса: повторная доставка того же вебхука MUST NOT добавлять сообщение в историю повторно и запускать повторную генерацию.

#### Scenario: Повторная доставка
- **GIVEN** сообщение `msg-1` уже обработано
- **WHEN** тот же вебхук с `msg-1` приходит снова
- **THEN** история не меняется, новое примечание не создаётся

### Requirement: История диалога по сделке
Система SHALL хранить в памяти историю сообщений клиента и менеджера по каждой сделке в порядке поступления и передавать её в `ReplyService` как `history` (без текущего сообщения, которое передаётся как `message`). Обрезка до `HISTORY_LIMIT` выполняется существующей логикой подготовки истории. После перезапуска процесса история теряется.

#### Scenario: Черновик учитывает предыдущие сообщения
- **GIVEN** по сделке `555` уже были сообщения клиента «Хочу Омега-3» и менеджера «Она в наличии»
- **WHEN** клиент пишет «А доставка в Казань?»
- **THEN** модель получает эти два сообщения в `history`, а «А доставка в Казань?» — в `message`

#### Scenario: Истории разных сделок не смешиваются
- **GIVEN** сообщения по сделкам `555` и `777`
- **WHEN** клиент пишет по сделке `777`
- **THEN** в `history` попадают только сообщения сделки `777`

### Requirement: Генерация только на сообщение клиента
Система SHALL запускать генерацию черновика только на сообщение с ролью `client`. Сообщение с ролью `manager` MUST только добавляться в историю сделки.

#### Scenario: Сообщение менеджера
- **WHEN** приходит исходящее сообщение менеджера по сделке `555`
- **THEN** оно добавлено в историю, модель не вызывается, примечание не создаётся

#### Scenario: Сообщение клиента
- **WHEN** приходит входящее сообщение клиента по сделке `555`
- **THEN** вызывается `ReplyService`, а результат записывается примечанием к сделке `555`

### Requirement: Результат в примечании к сделке
Система SHALL записывать результат генерации только как внутреннее примечание к сделке через `CrmClient`. Текст примечания MUST содержать черновик ответа клиенту и подсказку менеджеру (`manager_hint`); при срабатывании стоп-листа в ответе клиенту — ещё и исходный заблокированный черновик с пометкой. Сообщения клиенту система MUST NOT отправлять ни в каком режиме.

#### Scenario: Примечание с черновиком и допродажей
- **GIVEN** модель ответила по базе и предложила допродажу
- **WHEN** примечание записано
- **THEN** его текст содержит черновик ответа, название и цену допродажи и `why_now`

#### Scenario: Ответа нет в базе знаний
- **GIVEN** клиент спрашивает о том, чего нет в базе, и сервис вернул `needs_human=true`, `reason=no_kb_answer`
- **WHEN** примечание записано
- **THEN** оно содержит черновик с честным ответом, что информации нет, и строку «Нужен менеджер: ответа нет в базе знаний»

#### Scenario: Сбой модели
- **GIVEN** модель недоступна
- **WHEN** клиент пишет сообщение
- **THEN** примечание всё равно создаётся: шаблонный ответ и пометка, что черновик не сформирован

#### Scenario: Ошибка записи примечания
- **GIVEN** `CrmClient` вернул ошибку при записи
- **WHEN** фоновая задача завершается
- **THEN** ошибка записана в лог, процесс продолжает принимать вебхуки

### Requirement: Клиент CRM и режимы работы
Система SHALL обращаться к CRM только через интерфейс `CrmClient` с методом записи примечания к сделке. Режим задаётся `CRM_MODE`: `mock` (по умолчанию) использует `MockCrmClient`, хранящий примечания в памяти; `amo` использует `AmoCrmClient`, который отправляет `POST https://{AMO_SUBDOMAIN}.amocrm.ru/api/v4/leads/{lead_id}/notes` с `note_type=common` и заголовком `Authorization: Bearer {AMO_ACCESS_TOKEN}`. В режиме `amo` отсутствие `AMO_SUBDOMAIN`, `AMO_ACCESS_TOKEN` или `WEBHOOK_SECRET` MUST останавливать запуск с понятной ошибкой.

#### Scenario: Режим по умолчанию
- **GIVEN** `CRM_MODE` не задан
- **WHEN** сервис запущен и клиент написал по сделке `555`
- **THEN** примечание сохранено в памяти `MockCrmClient`, внешних HTTP-запросов к amoCRM нет

#### Scenario: Запрос AmoCrmClient
- **GIVEN** `CRM_MODE=amo`, `AMO_SUBDOMAIN=demo`, `AMO_ACCESS_TOKEN=tkn`
- **WHEN** записывается примечание к сделке `555`
- **THEN** отправлен `POST https://demo.amocrm.ru/api/v4/leads/555/notes` с `Authorization: Bearer tkn` и телом `[{"note_type": "common", "params": {"text": "…"}}]`

#### Scenario: Не хватает настроек amo
- **GIVEN** `CRM_MODE=amo` и не задан `AMO_ACCESS_TOKEN`
- **WHEN** сервис запускается
- **THEN** запуск останавливается с ошибкой, называющей недостающую настройку
